# 科室知识库绑定 与 自由库删除迁移 — 设计文档

- 日期: 2026-07-06
- 涉及仓库:
  - `shougang-group-knowledge-portal`（base: `master`）— 后台配置 UI + BFF 代理
  - `bisheng_2`（base: `mainline2`）— 绑定 admin API + 删除挂钩 + 迁移任务
- 状态: 待评审

## 1. 背景与目标

团队知识库（`knowledge_space_scope.level = team` 的知识空间）目前不区分归属。本需求引入两个概念，并在删除时保护数据：

1. **科室知识库**：管理员在后台把某个**已存在的团队知识库**绑定到一个部门后，该库即「科室库」。
2. **自由知识库**：没有绑定任何部门的团队知识库。
3. **删除迁移**：删除自由库时，自动找到「创建者所属部门 → 对应科室库」，把自由库的全部数据迁移过去，再删除自由库。

核心价值：自由库被删除时数据不丢失，而是归集到该部门的科室库。

## 2. 术语

| 术语 | 定义 | 判定 |
|---|---|---|
| 团队知识库 | `knowledge` 表 `type=SPACE` 且 `knowledge_space_scope.level='team'` 的空间 | 现有概念 |
| 科室知识库 | 已在 `department_knowledge_space` 建立绑定行的团队库 | `DepartmentKnowledgeSpaceDao.aget_by_space_id(space_id)` 非 null |
| 自由知识库 | 未建立绑定行的团队库 | 同上返回 null |
| 绑定 | `department_knowledge_space` 中「`department_id` ↔ `space_id`」一行 | 1 部门 : 1 科室库；1 空间 : 1 部门（既有唯一约束） |

> 注意：本需求的「科室库」= **给现有 team 库打绑定标记**，**不新建空间**。这与 bisheng 既有的 `DepartmentKnowledgeSpaceService.batch_create_spaces`（为部门**新建** DEPARTMENT 层级空间）语义不同——后者只作参考，不复用其创建流程。绑定后 `knowledge_space_scope.level` **保持 `team` 不变**，科室库仍属于「团队知识库」分类。

## 3. 现状分析（已具备的基础设施）

- **表 `department_knowledge_space`**（`bisheng/knowledge/domain/models/department_knowledge_space.py`）：已有 `department_id`/`space_id` 唯一约束、外键 CASCADE，以及 DAO 方法 `acreate` / `aget_by_space_id` / `aget_by_department_id` / `aget_space_id_by_department_id` / `aget_by_department_ids`。**直接复用，不新增表。**
- **用户→部门**：`UserDepartmentDao.aget_user_primary_department(user_id)`（主部门）、`aget_user_departments(user_id)`（全部）；`Department` 有物化路径 `path`（形如 `/1/2/3/`）可向上追溯祖先。
- **删除入口**：`KnowledgeSpaceService.delete_space(space_id)`（`knowledge_space_service.py:4910`），SPACE 专用，同步清理 向量(Milvus/ES)→MinIO→DB→FGA tuple→成员→channel sync。删除 API：`DELETE /knowledge_space/{space_id}`。
- **文件级复制**：`worker/knowledge/file_worker.py` 的 `copy_normal`（复制 MySQL 行 + MinIO 对象）与 `copy_vector`（用 `FakeEmbeddings` 把源向量原样 query→insert 到目标 collection/ES）。**可复用为迁移的文件级搬运。**
  - ⚠️ 外层编排 `file_copy_celery` 只处理 `type=NORMAL`，**不适用 SPACE**，需要新写一个 SPACE 版编排任务。
  - ⚠️ `copy_vector` 不重算向量、原样搬运，因此**源库与目标库 embedding 模型必须一致**，否则迁移后目标库检索失效。
- **统一 embedding**：`create_knowledge_space` 用 `workbench_llm.embedding_model.id` 建库（`knowledge_space_service.py:2226`），全平台一般统一模型，故模型不一致属**罕见**，但仍需前置校验兜底。
- **状态枚举**：`KnowledgeState.COPYING = 2` 已存在，可作「迁移中」状态。

## 4. 已确定的设计决策

| # | 决策点 | 结论 |
|---|---|---|
| D1 | 科室库定义 | 给现有 team 库加 `department_knowledge_space` 绑定行，不新建空间 |
| D2 | 绑定配置入口 | shougang portal 后台（AdminPage）→ BFF → bisheng 新 admin API |
| D3 | 迁移触发 | 自动挂钩到 `delete_space`，无需单独按钮 |
| D4 | 无法迁移时 | **阻断删除并报错**（删除前校验，数据不丢） |
| D5 | 科室库自身被删 | **禁止删除**，须先在后台解绑 |
| D6 | 迁移目标查找 | 从创建者主部门起，沿 `department.path` 向上找最近的已绑定科室库 |
| D7 | 迁移执行 | **异步后台**任务；源库进入「迁移中」并加删除锁；成功后自动删源库；失败回滚保留源库 |
| D8 | embedding 不一致 | 视为「无法迁移」，删除前校验阻断 |
| D9 | 绑定与权限 | **本期不自动改任何访问权限**，绑定仅是「库↔部门」元关系 |
| D10 | scope.level | 绑定后 `level` 保持 `team` 不变 |

```
│   admin_config.py (BFF 代理) ──┼─HTTP──▶│  GET    dept-knowledge/bindable-spaces│
│ backend/app/clients/bisheng.py │        │  GET    departments (可复用现有)     │
└────────────────────────────────┘        │                                     │
                                           │ delete_space() 前置挂钩:            │
   删除操作在 bisheng iframe UI 内触发 ───▶│  自由库→查目标科室库→投递迁移任务   │
                                           │                                     │

```

删除操作本身发生在用户直连的 bisheng 前端（iframe），因此**删除→迁移逻辑必须落在 bisheng backend 的 `delete_space` 链路**，与 portal 无关；portal 只负责绑定配置。

## 6. 数据模型

**不新增表、不新增字段**（除非迁移锁需要，见 §8）。全部复用 `department_knowledge_space`。

判定与查找封装到一个新 domain service（建议 `FreeSpaceMigrationService` 或并入 `DepartmentKnowledgeSpaceService`）：

- `is_department_space(space_id) -> bool`
- `resolve_target_department_space(creator_user_id) -> Optional[space_id]`：主部门→沿 `path` 祖先链→最近的绑定科室库
- `bind(space_id, department_id, operator)` / `unbind(space_id, operator)` / `list_bindings()` / `list_bindable_team_spaces()`

## 8. 功能 B：删除 → 迁移

### 8.1 挂钩点

在 `delete_space(space_id)` 最前面（权限校验后、实际清理前）插入分支判定。为避免污染通用 `delete_space`，建议：
- `delete_space` 开头调用 `FreeSpaceMigrationService.pre_delete_guard(space)`，由它决定「直接放行删除 / 阻断报错 / 转异步迁移」。

### 8.2 完整时序

```
delete_space(space_id):
  space = load(space_id); 校验存在 & type=SPACE & 非收藏
  guard = pre_delete_guard(space):
    binding = aget_by_space_id(space_id)
    if binding: raise 科室库禁止删除，请先解绑            # D5
    if scope.level != 'team':  正常删除（个人/公共等走原逻辑）
    # 自由 team 库:
    dept = aget_user_primary_department(space.user_id)
    if not dept: raise 无法迁移：创建者无主部门             # D4
    target_space_id = resolve_target_department_space(dept) # 沿 path 向上 D6
    if not target_space_id: raise 无法迁移：所属部门树无科室库 # D4
    target = load(target_space_id)
    if source.model != target.model: raise 无法迁移：embedding 模型不一致 # D8
    # 通过校验 → 转异步
    mark_source_migrating(space_id)   # state=COPYING + 删除锁，防重复删/迁
    enqueue space_migrate_celery(source_id=space_id, target_id=target_space_id, op_user)
    return MIGRATING   # delete_space 提前返回，不走同步删除

space_migrate_celery(source_id, target_id, op_user):
  分页遍历 source 的 KnowledgeFile:
    for f in page:
      if f.md5 in target_md5_set: continue        # 去重
      copy_normal(f, source, target, op_user)      # MySQL+MinIO
      # copy_normal 内部对 SUCCESS 文件调 copy_vector（Milvus+ES）
  if 全部成功:
    KnowledgeSpaceService.delete_space(source_id)  # 真正删源库（此时解锁）
  else:
    回滚 source 状态（去掉迁移中/删除锁），保留源库，记录失败原因/审计
```

### 8.3 迁移中状态 & 删除锁

- 源库置 `state=COPYING`，并加**删除锁**（防止迁移进行中被再次删除或编辑）。锁的落地方式二选一，实现期定：
  - (a) 复用 `is_favorite`-style 的保护标志：新增最小字段 `migrating: bool`（需 alembic 加列）；
  - (b) 仅用 `state=COPYING` + 在 `delete_space`/`update_knowledge_space` 前置判断拒绝。
  - 倾向 (b)（零 schema 变更），若不足再上 (a)。
- 迁移中源库对用户表现为只读/不可再删，UI 上可显示「迁移中」。

### 8.4 边界情况汇总

| 情况 | 处理 |
|---|---|
| 创建者无主部门 | 阻断删除，报错 |
| 主部门及所有祖先部门都无科室库 | 阻断删除，报错 |
| embedding 模型不一致 | 阻断删除，报错 |
| 目标科室库已有同 md5 文件 | 跳过该文件（去重） |
| 迁移中再次点删除 | 删除锁拒绝 |
| 单个文件复制失败 | 记录该文件失败；整体视为失败→回滚保留源库（不半迁半删） |
| 删除的是科室库本身 | 阻断，提示先解绑 |
| 删除的是个人/公共库 | 不受影响，走原 `delete_space` |

## 9. 非目标（YAGNI，本期不做）

- 不自动给部门成员授予科室库访问权限（D9）。
- 不支持 embedding 不一致时重嵌入迁移（改为阻断）。
- 不支持一个空间绑定多个部门 / 一个部门多个科室库（沿用既有唯一约束）。
- 不改动 bisheng 既有 `batch_create_spaces`（新建部门空间）流程。
- 不做迁移进度条/断点续传（失败即整体回滚重试）。

## 12. 风险 / 待确认

- **R1（base 分支）**：bisheng_2 实际在 `mainline2`，需确认从哪个分支切。
- **R2（迁移原子性）**：迁移与删源库跨 Milvus/ES/MinIO/MySQL 多存储，无分布式事务；采用「先全量迁移成功、再删源库；失败则保留源库」策略保证不丢数据（最坏是目标库出现半量已迁文件，但都带 md5，可重试去重）。
- **R3（super_admin token）**：BFF 调 bisheng admin API 需要具备 super_admin 身份的 token；确认用系统级 token 还是要求操作者本身是 admin。
- **R4（删除锁落地方式）**：§8.3 (a)/(b) 二选一，实现期定。
